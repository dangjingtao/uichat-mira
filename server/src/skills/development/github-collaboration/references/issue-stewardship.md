# Issue Stewardship

用于 Issue 的搜索、创建、更新、评论、关闭和重新打开。

## 创建前

1. 确认仓库与问题边界。
2. 使用 `github_issue.search` 搜索标题和正文中的近似关键词。
3. 对高相似结果读取详情。
4. 发现可能重复项时，先向用户说明差异，不直接创建。

## Issue 结构

一个可执行的 Issue 通常包含：

- 清晰、可搜索的标题；
- 背景或现象；
- 当前行为；
- 期望行为；
- 范围与非目标；
- 验收标准；
- 风险、依赖或复现信息；
- 合理的 labels / assignees。

不要为凑格式添加没有事实依据的标签、负责人或截止日期。

## 更新前

先用 `github_issue.get` 读取当前标题、正文、状态、标签、负责人和评论。更新时明确区分：

- **补充事实**：追加正文或评论；
- **改变任务合同**：更新标题、正文或验收标准；
- **改变状态**：close / reopen；
- **改变所有权**：assignees / labels / milestone。

较小的进展说明优先使用评论，不要反复重写正文。

## 关闭与重开

关闭前确认：

- 验收标准是否满足；
- 是否有未处理评论或阻塞项；
- `completed` 与 `not_planned` 哪个原因真实；
- 是否应留下总结评论。

重新打开时说明新事实或未完成原因。

## 回读验证

写入后重新读取 Issue，并向用户返回：

```text
Issue #number
标题
状态 / state reason
labels
assignees
链接
本次变化
```

## 完成标准

- 创建前完成重复项搜索；
- 写入内容可执行，不只是聊天摘要；
- 状态变化有理由；
- 写入后已回读确认；
- 未经审批没有远程修改。
