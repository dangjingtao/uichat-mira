# 发布博客或文档

用于 `publish_content` 操作。

博客和文档共享同一套发布闭环，只在内容类型、目录、frontmatter 和导航处理上不同。

## 1. 参数合同

### 阻塞参数

| 参数 | 说明 | 缺失处理 |
| --- | --- | --- |
| `targetSite` | 目标本地站点或 GitHub 仓库 | 当前任务已明确则继承，否则询问 |
| `contentSource` | 正文、附件、已有文件或可读取来源 | 没有内容时询问 |
| `content.kind` | `blog` / `doc` | 用户明确则直接使用；确实无法判断时询问 |

### 可推断参数

| 参数 | 推断方式 |
| --- | --- |
| `title` | 用户明确标题或正文第一个标题 |
| `summary` | 根据正文生成短摘要 |
| `slug` | 根据标题和站点约定生成，并检查冲突 |
| `date` | 新博客使用当前日期；迁移或更新保留原日期 |
| `author` | 使用站点已配置作者；没有则留空，不虚构 |
| `category` | 用户指令、正文语义或相邻内容约定 |
| `status` | “发 / 发布 / 上线”→ `published`；“写 / 整理 / 准备”→ `draft` |
| `navigation` | 根据站点内容发现和导航约定判断是否需要更新 |

## 2. 内容类型判断

优先采用用户明确表达：

```text
博客 / 随笔 / 更新日志 / 发布记录
→ blog

文档 / 指南 / 教程 / API 说明 / 使用说明
→ doc
```

仍然模糊时只问：

```text
这篇内容放在博客，还是文档目录？
```

不要要求用户填写完整 frontmatter 表单。

## 3. 读取当前站点

写入前至少读取：

- MiraDocs 配置和内容目录；
- 同类内容的路径、命名和 frontmatter；
- 当前导航或自动发现规则；
- 是否已有相同标题、slug 或永久链接；
- 图片、附件和相对链接的资源约定；
- 当前分支、活跃 PR 和部署方式。

不能用其他 MiraDocs 站点的目录约定替代当前站点事实。

## 4. 发布草案

写入前展示关键字段：

```text
目标站点：dangjingtao/tomz-lab
类型：博客
标题：MiraDocs 0.1 发布记录
路径：blogs/miradocs-0-1-release.md
状态：立即发布
日期：2026-07-26
分类：工程记录
导航：按现有自动发现规则，无需手工更新
```

用户可以直接纠正标题、类型、路径、状态、日期或分类。

如果用户只说“发上去”，不要额外盘问所有可推断字段。

## 5. 发布施工流程

```text
确定目标站点
→ 读取站点配置和相邻内容
→ 解析或整理正文
→ 生成并展示发布草案
→ 检查重名、永久链接和资源路径
→ 创建独立分支或使用当前已批准施工分支
→ 写入内容
→ 必要时更新导航或索引
→ 回读文件
→ 执行内容发现和静态构建
→ 验证目标路由
→ 用户要求上线时检查 CI / 部署
→ 返回页面地址、提交和验证结果
```

## 6. 内容规则

### 新建内容

- 正文是主内容，不因“统一风格”大幅重写用户事实、观点或语气；
- 标题、摘要和 frontmatter 应服务于可读性与内容发现；
- slug 必须稳定、可读并符合当前站点约定；
- 同名文件、标题或路由冲突时先说明冲突，不直接覆盖；
- 作者无法确认时留空，或使用当前站点已经配置的默认作者；
- 图片和附件必须确认来源可访问，并转换为站点支持的资源路径。

### 更新内容

- 先读取旧文件和当前路由；
- 普通修改默认保留原 slug、日期和永久链接；
- 明确区分更新现有内容与另存为新内容；
- 用户只要求修正文案时，不顺手改目录结构或导航体系；
- 修改后回读关键段落和 frontmatter。

### 迁移内容

- 保留原作者、原日期、标题语义和永久链接；
- 保留外链、引用和图片来源；
- 格式转换不得造成内容丢失；
- 批量迁移先做小样，验证后再扩大；
- 如无法保留旧路径，必须提供重定向或兼容方案。

### 删除或下线

删除不属于普通发布。转入 `maintain_site` 的破坏性操作规则：定位精确文件和路由，说明链接影响，并询问删除、下线还是保留重定向。

## 7. 导航处理

先判断站点采用：

```text
自动内容发现
显式导航配置
混合模式
```

- 自动发现已覆盖目标目录时，不重复维护导航；
- 显式导航站点只有在用户目标需要入口时才修改；
- 导航修改必须验证对应页面路由；
- 不因发布一篇博客重构全站导航。

## 8. 草稿与发布

```text
用户说“写一篇 / 整理一下 / 准备一篇”
→ 默认 draft

用户说“发 / 发布 / 上线”
→ published
```

如果当前站点没有草稿协议，不要伪造 `draft` 字段。应根据站点实际约定选择草稿目录、frontmatter 状态或只创建未合并分支。

## 9. 验证

至少覆盖：

- 文件已写入并能回读；
- frontmatter 符合当前站点约定；
- 内容发现能找到新内容；
- 目标路由没有冲突；
- 本地静态构建结果明确；
- 图片、附件和主要站内链接可解析；
- 用户要求上线时，CI / Pages / 部署状态已回读。

## 10. 完成标准

- 内容路径、类型、标题和状态明确；
- 内容文件已写入并回读；
- 原有内容身份和链接语义未被无意破坏；
- 内容发现、目标路由和静态构建结果明确；
- 用户要求上线时，远程 CI 或部署结果明确；
- 返回内容路径、页面地址、commit 或 PR；
- 未完成的图片、导航、域名或部署问题被明确列出。
