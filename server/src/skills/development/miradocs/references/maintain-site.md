# 维护已有 MiraDocs 站点

用于 `maintain_site` 操作。

V1 只覆盖日常站点维护，不扩张成通用 CMS 或项目管理系统。

## 1. 支持范围

```text
站点配置
  名称、描述、Logo、主色、风格预设、作者信息

导航与内容结构
  导航项、栏目、首页入口、文档与博客目录

内容生命周期
  修改、下线、删除、重命名、链接兼容

诊断与修复
  内容未发现、路由失效、构建失败、部署失败

升级与迁移
  MiraDocs 版本升级、已有内容迁入、配置兼容

部署设置
  GitHub Pages、自定义域名和现有工作流检查
```

## 2. 参数合同

维护任务通常只需要：

```text
目标站点
要改变或诊断的对象
期望结果
```

当前对话没有目标站点时，只问：

```text
要修改哪个本地项目或 GitHub 仓库？
```

目标站点明确后先读取当前配置，不要求用户重新填写整套站点参数。

## 3. 修改站点配置

先读取实际配置与相关页面，再展示精确差异：

```text
site.name
- Mira Docs
+ Tomz Lab
```

常见修改：

- 站点名称与描述；
- 首页标题和入口；
- Logo、主色和已有风格预设；
- 作者信息；
- 文档、博客和导航配置；
- GitHub Pages 与自定义域名。

只修改用户要求的对象。不得借一次标题修改重构主题、路由或内容结构。

## 4. 内容生命周期

### 修改

- 读取旧文件、frontmatter 和路由；
- 保留未要求改变的 slug、日期、作者和分类；
- 展示关键差异；
- 写入后回读并验证目标路由。

### 重命名或移动

- 明确旧路径与新路径；
- 检查站内链接、导航和外部永久链接；
- 优先保留原 slug；
- 必须更改链接时提供重定向或兼容方案。

### 下线或删除

必须定位精确文件和页面：

```text
将删除 blogs/old-post.md，并使 /blogs/old-post/ 失效。
要直接删除、改为草稿，还是保留重定向？
```

不得根据“旧的那篇”“没用的页面”等模糊表达直接删除。

## 5. 诊断流程

```text
读取失败现象和当前状态
→ 定位失败层：内容 / 配置 / 构建 / 部署
→ 复现问题或读取 CI / 部署证据
→ 说明原因、影响和建议修复
→ 经批准后修改
→ 重跑失败层及必要的上层验证
→ 回读结果
```

### 内容未发现

检查：

- 文件是否位于当前内容发现目录；
- frontmatter 是否有效；
- 扩展名、命名和路径是否符合约定；
- 内容发现配置是否包含目标目录；
- 是否存在路由或 slug 冲突；
- 构建日志是否明确跳过或拒绝该文件。

### 路由或链接失效

检查：

- 当前生成路由；
- base path 与部署子路径；
- 相对链接和资源路径；
- 重命名、移动或历史 permalink；
- 静态产物中目标页面是否存在。

### 构建失败

优先读取并复现最小失败层：

```text
依赖安装
TypeScript
内容解析
Vite 构建
静态产物验证
```

不要把未知问题直接归因于 MiraDocs，也不要为了让命令通过添加未经批准的 fallback。

### 部署失败

读取：

- 当前部署工作流；
- 默认分支与触发条件；
- 最近 Actions run；
- 构建输出目录；
- Pages base path、自定义域名与权限；
- 本地构建和远程构建差异。

GitHub 站点优先调用：

```text
github_repository.get_pages
→ 读取 Pages 是否启用、build type、source、域名、HTTPS 和最终 URL

github_repository.configure_pages
→ 经审批后启用或修改 workflow / branch 模式、域名与 HTTPS
→ 写后再次读取最终 Pages 状态
```

没有读取远程状态前，不声称部署失败已经修复。

## 6. 升级 MiraDocs

```text
读取当前版本和锁文件
→ 查看目标版本当前发布与迁移说明
→ 判断 breaking changes
→ 创建独立分支
→ 更新依赖与必要配置
→ frozen install
→ TypeScript
→ 静态构建
→ 验证关键路由和内容数量
→ 创建或更新 PR
→ 检查 CI
```

升级不得覆盖用户内容。需要迁移配置或内容时，先展示变更范围和回滚点。

## 7. 迁移已有内容

- 先盘点源内容数量、目录、格式和资源；
- 选取少量代表性内容做迁移样例；
- 保留标题、作者、日期、永久链接和外链语义；
- 验证内容发现、路由、图片和构建；
- 样例通过后再扩大批次；
- 迁移结果必须可回滚。

批量迁移属于高影响操作，执行前展示范围、目标目录和可能冲突。

## 8. 破坏性操作

以下操作必须展示精确对象和影响：

```text
删除内容
覆盖已有仓库文件
更改永久链接
修改默认分支或部署工作流
替换自定义域名
批量迁移
```

审批仍由现有 Harness 与远程工具合同负责。Skill 不能用模糊确认代替精确 invocation。

## 9. 验证范围

根据变更选择必要验证，不需要每次都跑无关检查：

| 变更 | 最低验证 |
| --- | --- |
| 文案或元信息 | 回读文件、内容发现、目标路由 |
| 导航或内容结构 | 类型检查、构建、入口和链接 |
| 依赖或配置 | frozen install、类型检查、构建 |
| 路由或 base path | 静态产物与部署路径 |
| 部署工作流 | 本地构建、远程 Actions / Pages 状态 |
| 删除或迁移 | 旧链接影响、重定向、内容数量与构建 |

## 10. 完成标准

- 修改前的当前事实已读取；
- 变更差异和影响明确；
- 破坏性操作已展示精确对象并经过现有审批；
- 写入后文件已回读；
- 与变更相关的类型检查、构建、路由或部署验证已完成；
- 未经验证的部分没有被描述为成功；
- 返回可核验的路径、commit、PR、CI 或部署状态。
