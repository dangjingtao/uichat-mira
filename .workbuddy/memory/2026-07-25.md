## MCP 模块「国内慢」评估（只读研究，未改代码）
- 用户实际痛点 = **市场列表拉不下来**（不是 npx 拉包）。列表数据源硬编码境外 `https://registry.modelcontextprotocol.io/v0.1/servers`（`server/src/mcp/marketplace.ts:3`，官方 registry 跑在 Cloudflare Worker/DynamoDB，无国内 CDN/镜像），国内要么极慢要么 20s 超时（`REGISTRY_TIMEOUT_MS=20000`）→ 列表加载失败。
- 关键发现：项目自家设计文档 `docs/architecture/external-mcp-marketplace.md:523-538` 早已规划此方向——默认官方 registry，国内友好 source = 镜像/自托管 curated registry/静态 JSON；MVP 先支持 runtime/env override（例如 `MCP_REGISTRY_URL`），后续再补 UI source selector。即代码改动方向已被文档拍板。
- 已埋好但未接线的能力：`fetchMcpMarketplaceServers(input.sourceUrl ?? DEFAULT_REGISTRY_URL)`（`marketplace.ts:331`）已支持自定义目录 URL；前端 `Mcp/index.tsx` 已有 `sourceUrl` state（从响应回填、安装时透传 `registryUrl`），但首次加载列表的 `GET /mcp/marketplace/servers`（`routes.ts:182`，`getMcpMarketplaceServers` at `tools.ts:297`）既不读 env 也不传 sourceUrl，永远走境外默认。5 分钟缓存仅兜底、救不了首次失败。
- 修复路径（按文档与现有 plumbing，改动小）：① 读 `MCP_REGISTRY_URL` env / `runtime.config.cjs` 的 `mcp.marketplaceUrl` 作为默认 source，替换硬编码；② 路由+前端透传可选 `sourceUrl`；③ 用户侧提供国内 endpoint（自托管 registry 镜像 / 静态 JSON 快照）。官方 registry 无国内镜像，故"镜像"需自建或打包静态目录。
- 注：npx 拉包慢（stdio-session env 注入 NPM_CONFIG_REGISTRY）是另一个独立问题，非本次用户诉求。

## 国内 MCP 目录源调研（只读，2026-07-25）
- 结论：没有"官方 registry API 的国内镜像"（即直接替换 `DEFAULT_REGISTRY_URL` 就能 drop-in 用的）。官方 registry 开源且允许自建 sub-registry（`modelcontextprotocol/registry` 仓库即数据/OpenAPI 规范），但无人公开运营免费国内兼容镜像。
- 国内友好替代目录（格式 ≠ 官方，需 adapter 或自托管）：
  - **魔搭 ModelScope MCP 广场 (modelscope.cn/mcp)**：阿里背景、全中文、上千款、提供 OpenAPI 可被客户端（Cherry Studio/通义灵码/Kimi）集成——最成熟，但返回结构不同，需写字段映射层。
  - 阿里云百炼 / 腾讯云 MCP：偏托管服务，非通用目录 API。
  - mcp.so：全球最大集合、支持中文 UI，但海外，国内同样慢。
- 推演给用户的三条路：A) 自托管官方兼容 sub-registry 部署国内（严格 drop-in，API 一致）；B) 打包静态 JSON 快照本地返回（零网络、国内秒开、不自动更新）；C) 接魔搭 MCP 广场（生态最全、需写 adapter）。

## 接魔搭 MCP 广场：业务流程适配分析（只读，2026-07-25）
- 魔搭列表接口 `PUT /openapi/v1/mcp/servers`（body: search / filter.category / filter.is_hosted / page_number / page_size）只返回摘要（id / name / chinese_name / description / categories / tags / logo_url 等），**不含 transport**。
- 连接配置在详情 `GET /openapi/v1/mcp/servers/{id}`：`is_hosted`、`env_schema`、`server_config[]`、`operational_urls[]`(url / transport_type: sse|streamable_http / auth_required / expiration)；hosted 还需 `POST /deploy` 再取 `operational_urls?get_operational_url=true`。
- 与我们"列表自带 transports"模型根本不同，适配要点：
  1. 列表→详情二次拉取（改 marketplace 获取模型，架构级，非单纯 env override）。
  2. 我们 transport 仅 `streamable-http|stdio`（`external.ts:16/479/513/532` 由 SQLite CHECK 锁死），魔搭有 `sse` → 需扩 kind 或 SSE 服务不可用。
  3. marketplace normalizer 把 package 强转 `npx -y`（`marketplace.ts:170-179`），魔搭多为 uvx/docker → adapter 必须保留原始 command，不能套 npx。
  4. 需新增 ModelScope API Token 凭证（详情/部署要 Bearer；列表可能无需但稳妥带）。
  5. hosted 的 operational_url 有过期（`expiration` 字段，如 24h）→ connect 需处理过期重连/刷新。
  6. 利好：streamable-http 的 Bearer + customHeaders 我们已支持（`external.ts:1091-1102`），魔搭托管鉴权可直接对接；env_schema 可映射进现有 ConfigModal。
- 结论：魔搭属"不同 schema 源"，超出设计文档 MVP（env override 假设 drop-in 兼容），更接近文档 `external-mcp-marketplace.md` 里的"UI source selector + adapter"远期项。属架构级改动，需 owner 批准再动。
